# AI 中转站双轴分层架构

> 版本：v1.0
> 适用场景：自建 AI 中转站 / 多上游路由网关 / 内部统一 API 平台
> 原则：只讨论合规、可持续、可运营的供给结构与成本分层

---

## 一、这份文档解决什么问题

做 AI 中转站时，一个常见误区是把所有“便宜来源”都直接当成技术层来设计。

更合理的做法，是把系统拆成两条轴：

1. **技术运行层（Runtime Layers）**
   决定一次请求在运行时应该走哪类能力、哪种稳定性和哪种降级链。

2. **成本/采购层（Procurement Layers）**
   决定同一种技术能力，是通过什么采购方式、什么结算方式、什么区域/商务条件拿到的。

这样拆开以后，架构会更清楚：

- 技术层负责“怎么跑”
- 成本层负责“怎么买”
- 路由系统负责“这次请求跑哪层”
- 商务系统负责“这层的成本是怎么来的”

---

## 二、总览：推荐的双轴结构

### 2.1 技术运行层（推荐 5 层）

- **T1 Premium Direct Layer**：高价高稳实时层
- **T2 Managed Cloud Layer**：主力托管云层
- **T3 Economy Expansion Layer**：低成本扩容层
- **T4 Fallback Layer**：兜底降级层
- **T5 Async / Batch Layer**：异步批处理层

### 2.2 成本/采购层（推荐 5 层）

- **P1 Public Rate Layer**：公开价采购层
- **P2 Regional Pricing Layer**：区域价格采购层
- **P3 Local Entity Procurement Layer**：本地主体商务采购层
- **P4 Committed Capacity Layer**：承诺容量采购层
- **P5 Cost-Optimization Mode Layer**：低价处理模式层

---

## 三、技术运行层定义

> 技术层的核心问题是：请求进入网关之后，应该走什么样的能力层级？

### T1：Premium Direct Layer（高价高稳实时层）

#### 定义
面向高价值、低容错、对时延和稳定性要求最高的请求。

#### 适合放什么
- 官方直连 API
- 企业合同类高优先级渠道
- 最稳定、最可控、最容易承诺 SLA 的上游

#### 适合什么请求
- VIP 用户实时请求
- 长上下文
- Tool use / function calling
- 生产环境关键路径
- 需要优先成功率的场景

#### 角色
- 保口碑
- 保成功率
- 保高价值客户体验

#### 不适合什么
- 普通低价套餐跑量
- 离线任务
- 批量任务

### T2：Managed Cloud Layer（主力托管云层）

#### 定义
由云厂商托管的模型服务层，是大部分商业平台最适合承接主力流量的一层。

#### 适合放什么
- Bedrock
- Vertex AI
- Azure OpenAI / Azure AI Foundry
- 其他主流托管模型服务

#### 适合什么请求
- 普通实时在线请求
- 大多数标准付费用户
- 主力承载层

#### 角色
- 主力出量
- 平衡成本和稳定性
- 统一区域和企业采购能力

#### 特点
- 不一定最便宜
- 但通常比直接管理大量上游账号更省运维成本
- 商务上更容易扩容和谈判

### T3：Economy Expansion Layer（低成本扩容层）

#### 定义
以更低成本承接峰值、普通流量和价格敏感型请求的扩容层。

#### 适合放什么
- 成本较低的正规聚合推理平台
- 成本更敏感的标准 API 渠道
- 部分普通付费用户默认层

#### 适合什么请求
- 普通套餐
- 峰值扩容流量
- 对时延要求中等的实时请求
- 成本优先于极致稳定的流量

#### 角色
- 做毛利
- 做扩容
- 承接非核心实时请求

#### 风险点
- 质量波动可能比 T1 / T2 更大
- 区域差异和可用性不一定稳定
- 必须有健康检查和失败切换机制

### T4：Fallback Layer（兜底降级层）

#### 定义
当上层不可用、预算过高或系统进入保护模式时，用于兜底的降级层。

#### 适合放什么
- 替代模型
- 开源模型
- 自托管模型
- 便宜但能力较弱的模型

#### 适合什么请求
- 总结
- 改写
- 分类
- embedding
- 审核
- 上层故障时的临时兜底聊天能力

#### 角色
- 保服务不断
- 保成本不失控
- 在故障时保持最小可用能力

#### 关键原则
- **必须透明降级**
- 不要把低层模型伪装成高层模型
- 日志中要能看到实际命中层级和实际模型

### T5：Async / Batch Layer（异步批处理层）

#### 定义
专门承接不要求秒级响应的任务，用更低的处理模式换更低的成本。

#### 适合放什么
- Batch API
- 异步队列
- Flex / 延迟容忍型服务层
- 低价离线推理能力

#### 适合什么请求
- 批量总结
- 批量改写
- embeddings 批处理
- 数据清洗
- 报表生成
- 夜间任务
- 后台异步任务

#### 角色
- 最大化降低综合成本
- 把低价值任务从实时通道剥离出去
- 提高整个平台单位利润

#### 关键原则
- 实时与异步必须逻辑隔离
- 不能让低优先级任务挤占实时资源

## 四、成本/采购层定义

> 成本层的核心问题是：同样一种技术能力，是通过什么方式拿到的？

### P1：Public Rate Layer（公开价采购层）

#### 定义
直接以公开价格采购，没有复杂商务条件。

#### 适合什么阶段
- MVP
- 早期验证阶段
- 小规模使用

#### 优点
- 接入简单
- 价格透明
- 启动快

#### 缺点
- 单位成本往往不是最低
- 缺少区域价和商务折扣空间

### P2：Regional Pricing Layer（区域价格采购层）

#### 定义
利用服务商允许的区域价、区域结算、区域资源差异来做采购优化。

#### 适合什么阶段
- 已经开始关注云端区域成本结构
- 存在明显区域价差或区域资源配置差异

#### 优点
- 在合规前提下可能拿到更低的区域价格
- 有机会优化结算与资源配置

#### 缺点
- 不适用于所有供应商
- 需要严格确认支持地区、税务和结算条件

#### 注意
- 这里说的是**合规区域价格**
- 不是通过虚假主体或借壳主体规避地区限制

### P3：Local Entity Procurement Layer（本地主体商务采购层）

#### 定义
通过真实当地公司、真实当地税务与银行结算能力，获取更合适的商务报价、代理报价或采购条件。

#### 适合什么阶段
- 已有真实海外主体
- 采购量已经达到可谈商务的规模
- 希望把成本优势做成长期能力

#### 优点
- 商务空间更大
- 结算路径更顺
- 税务与付款更规范
- 更适合谈包量、企业价、代理价

#### 缺点
- 需要真实经营实体
- 需要合规材料
- 需要更完整的财税与法务配合

#### 重要说明
“非洲真实主体采购”如果要放进架构里，更适合作为 **P3 的一个实例**，而不是单独的技术运行层。

### P4：Committed Capacity Layer（承诺容量采购层）

#### 定义
通过预留吞吐、承诺采购、保底用量、保留实例等方式，用固定承诺换更稳定的容量和更优的单位成本。

#### 适合什么阶段
- 流量可预测
- 主力模型已经稳定
- 平台需要更稳定的容量保障

#### 优点
- 容量稳定
- 单位成本可优化
- 适合企业级平台

#### 缺点
- 需要资金承诺
- 预测不准会浪费
- 灵活性下降

### P5：Cost-Optimization Mode Layer（低价处理模式层）

#### 定义
不改变上游供应商，只通过不同处理模式降低成本。

#### 常见方式
- Batch
- Flex
- Prompt caching
- 异步队列
- 预生成 / 预计算

#### 优点
- 最容易直接见到成本优化效果
- 实施风险低
- 对运行时架构改动相对小

#### 缺点
- 不适合强实时场景
- 需要产品侧明确区分任务类型

## 五、为什么“非洲真实主体采购”更适合放在成本层

如果有真实的当地经营主体，并且它能合法开户、结算、履约，那么它带来的优势通常是：

- 更容易接入本地或区域化商务采购
- 更容易走本地付款和税务链路
- 更可能拿到区域价或商务价
- 更适合做长期稳定采购

这些优势都属于“怎么买”，而不是“请求怎么跑”。

因此更合理的命名是：

- **P3-Local Entity Procurement（本地主体商务采购）**
- 或者更具体一点：**P3-Africa Entity Procurement（非洲本地主体商务采购实例）**

而不建议命名成：

- “非洲 KYC 层”
- “低价实名层”
- “区域绕路层”

因为这些名称会让架构看起来像是在绕规则，而不是在做合规采购优化。

## 六、双轴映射：技术层 × 成本层

下面是一种推荐映射方式。

| 运行层 | 主要职责 | 可挂接的采购层 | 说明 |
|---|---|---|---|
| T1 Premium Direct | 高价值实时请求 | P1 / P3 / P4 | 既可用公开价，也可用企业商务或承诺容量 |
| T2 Managed Cloud | 主力在线承载 | P1 / P2 / P3 / P4 | 最适合叠加区域价与商务采购 |
| T3 Economy Expansion | 低成本扩容 | P1 / P2 / P3 | 重点看单价、区域价和供给弹性 |
| T4 Fallback | 兜底降级 | P1 / P3 / P5 | 重点是成本和可用性，不追求顶级质量 |
| T5 Async / Batch | 批处理与异步 | P5 / P2 / P3 / P4 | 最适合用低价处理模式与区域/商务采购叠加 |

### 7.1 对外命名（给团队、投资人、业务方）

建议用中性、可解释、能长期沿用的名字：

#### 技术层
- Premium Layer
- Managed Layer
- Economy Layer
- Fallback Layer
- Async Layer

#### 成本层
- Public Rate Procurement
- Regional Procurement
- Local Entity Procurement
- Committed Capacity Procurement
- Cost-Optimization Mode

### 7.2 内部命名（给研发、运维、财务）

- T3 Economy Expansion
- T4 Fallback
- T5 Async Batch

- P1 Public Rate
- P2 Regional Pricing
- P3 Local Entity Procurement
- P4 Committed Capacity
- P5 Cost-Optimization Mode

## 八、路由设计建议

### 8.1 技术层路由

先决定“请求应该走哪种运行层”：

```text
VIP实时请求 -> T1 -> T2 -> T4
普通实时请求 -> T2 -> T3 -> T4
低价套餐请求 -> T3 -> T4
后台任务/离线任务 -> T5
```

### 8.2 成本层选择

在已经确定技术层后，再决定用哪种采购来源：

```text
T2 Managed Cloud
  -> 优先 P3 本地主体商务采购
  -> 其次 P2 区域价格采购
  -> 再次 P1 公开价采购
```

或者：

```text
T5 Async Batch
  -> 优先 P5 低价处理模式
  -> 如可叠加，则使用 P2 区域价
  -> 如采购量大，则升级到 P4 承诺容量
```

### 8.3 关键原则

- 先按**技术层**决定“应该怎么跑”
- 再按**成本层**决定“这层从哪买最划算”
- 不要反过来：不要因为某条采购便宜，就让所有请求都走它

## 九、套餐映射建议

### 9.1 VIP 套餐
- 主路由：T1
- 降级链：T2 -> T4
- 采购优先：P3 / P4

### 9.2 标准付费套餐
- 主路由：T2
- 降级链：T3 -> T4
- 采购优先：P2 / P3 / P1

### 9.3 经济型套餐
- 主路由：T3
- 降级链：T4
- 采购优先：P2 / P1

### 9.4 批处理套餐 / 内部异步任务
- 主路由：T5
- 采购优先：P5 -> P2 -> P3

## 十、系统实现建议

### 10.1 数据模型至少要能表达两层信息

#### 请求命中信息
- request_id
- user_id
- model_requested
- runtime_layer_hit（T1~T5）
- actual_provider
- actual_model
- response_mode（realtime / async）

#### 采购与成本信息
- procurement_layer_hit（P1~P5）
- billing_entity
- region
- cost_currency
- input_cost
- output_cost
- total_cost
- sell_price
- margin

### 10.2 路由器要分成两个阶段

#### 阶段一：运行层选择器
输入：
- 用户等级
- 请求类型
- 模型需求
- 是否实时
- 上下文长度
- 是否工具调用
- 当前系统负载

输出：
- T1 / T2 / T3 / T4 / T5

#### 阶段二：采购来源选择器
输入：
- 已选中的 T 层
- 当前区域
- 采购成本
- 供应可用性
- 商务优先级
- 是否命中 batch/cache/flex 规则

输出：
- P1 / P2 / P3 / P4 / P5 对应的具体供应通道

## 十一、什么时候可以把“非洲真实主体采购”单独写进系统

建议满足以下条件后再单独挂出来：

1. 该主体是真实经营主体
2. 有独立税务和银行结算能力
3. 对应采购价格或结算条件确实更优
4. 该路径能长期复用，而不是一次性机会
5. 财务与法务能对账和解释

满足这些条件后，可以在系统中写成：

- `P3-AF-Entity-Cloud`
- `P3-AF-Regional`
- `P3-AF-Managed`

也就是作为 **P3 的子类**，而不是一个新的 T 层。

---

## 十二、最终建议

### 如果只做一个简单版本
直接上：

- 技术层：4 层
  - T1 Premium
  - T2 Managed
  - T3 Economy
  - T4 Fallback

- 成本层：3 层
  - P1 Public Rate
  - P3 Local Entity Procurement
  - P5 Cost Optimization Mode

这是最容易先跑起来的版本。

### 如果做成成熟商业化平台
建议上：

- 技术层：5 层
- 成本层：5 层
- 路由采用双阶段选择
- 每次请求同时记录 T 层命中和 P 层命中

---

## 十三、一句话总结

**技术层回答“请求怎么跑”，成本层回答“能力怎么买”。**

所以：

- 官方 API、云托管、聚合平台、开源降级、Batch/Flex 这些属于 **技术运行层**
- 公开价、区域价、本地主体商务采购、承诺容量、低价处理模式这些属于 **成本/采购层**
- “非洲真实主体采购”如果合规真实，更适合定义为 **P3 的一个实例**，而不是新的技术运行层
